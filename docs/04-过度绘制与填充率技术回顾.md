# Overdraw、Early-Z 与 Fill Rate 技术回顾

本文回顾 `04.2 Overdraw / Fill Rate` 实验中涉及的关键概念，重点回答以下问题：

- 为什么桌面电脑上最初看不出明显差距；
- 为什么 Opaque 模式增加层数后 GPU 时间变化可能很小；
- Fragment Shader 中的循环是否真的执行；
- 深度测试、光栅化与 Fragment Shader 的先后关系；
- 应该使用 Unity Profiler 的哪个模块验证结果。

## 1. 实验控制变量

Demo 使用多层完全重叠的 Quad，对比两种渲染状态：

| 模式 | Render Queue | Blend | ZWrite | 预期行为 |
|---|---|---|---|---|
| Opaque | Geometry | `One Zero` | On | 前层写入深度，后层可能被 Early-Z 剔除 |
| Transparent | Transparent | `SrcAlpha OneMinusSrcAlpha` | Off | 各透明层不互相写深度，需要重复着色和混合 |

两种模式保持以下内容一致：

- Quad 数量；
- Renderer 数量；
- 材质实例数量；
- 几何形状和屏幕覆盖率；
- Fragment Shader 主体；
- Fragment Shader 循环次数。

因此，实验不是通过减少透明模式以外的 Draw Call 制造结果，而是比较深度写入、深度剔除和 Alpha Blend 对片元成本的影响。

## 2. Draw Call 到屏幕颜色的大致流程

单层 Quad 的逻辑渲染流程可以简化为：

```text
Draw Call
  ↓
Vertex Shader
  ↓
图元装配与裁剪
  ↓
光栅化
  生成候选片元
  ↓
Early-Z / Early Stencil（硬件和 Shader 条件允许时）
  ↓
Fragment Shader
  包含 Demo 中的片元计算循环
  ↓
可能的 Late-Z / Late Stencil
  ↓
颜色混合与 Render Target 写入
  ↓
深度写入（ZWrite On 时）
```

这是理解流程的逻辑模型，不代表 GPU 会逐像素串行工作。GPU 会并行处理大量片元，常见执行形式包括 2×2 Fragment Quad、Wave/Warp，以及基于 Tile 的分块处理。

## 3. Pixel、Fragment 与 Sample 的区别

这几个术语不能完全互换：

- **Pixel**：最终 Render Target 中的一个像素位置；
- **Fragment**：一个三角形对某个像素位置产生的候选颜色贡献；
- **Sample**：开启 MSAA 后，一个像素中用于覆盖率和深度判断的采样点。

同一个最终像素可能收到多个三角形、多个透明层产生的 Fragment。重复处理这些 Fragment，就是 Overdraw 的来源之一。

GPU 通常以 2×2 Fragment Quad 执行 Fragment Shader，以便计算纹理导数。边缘处还可能出现只参与导数计算、不写入最终颜色的 Helper Invocation。因此，“实际 Fragment Shader 调用数”等概念通常不会与最终像素数严格相等。

## 4. Shader 循环在哪里执行

Demo 中的循环位于 Fragment Shader 内部：

```hlsl
half4 Frag(Varyings input) : SV_Target
{
    float2 value = input.uv * 2.0 - 1.0;
    float signal = 0.0;

    for (int iteration = 0;
         iteration < (int)_FragmentIterations;
         iteration++)
    {
        value = frac(
            value * 1.6180339 +
            float2(0.137, 0.173) * (iteration + 1.0));
        signal += dot(value, value);
    }

    half modulation = (half)(0.9 + frac(signal * 0.13) * 0.1);
    return half4(_BaseColor.rgb * modulation, _BaseColor.a);
}
```

正确的表述不是“先执行循环，再执行 Frag”，而是每次 Fragment Shader Invocation 都会执行 Frag 函数，循环是该函数的一部分。

循环的计算结果最终参与输出颜色，因此编译器不能把整个循环当作无用代码直接删除。驱动仍可能对循环形式和指令调度做优化，但不会在保持结果不变的前提下凭空省略其效果。

## 5. 为什么 Opaque 增加层数后变化不大

假设 Unity 和 GPU 将最靠近摄像机的不透明层优先处理：

```text
第 1 层：
深度测试通过
→ 执行 Fragment Shader 循环
→ 写入颜色
→ 写入深度

第 2～128 层：
光栅化产生候选片元
→ Early-Z 发现片元位于已有深度之后
→ 提前拒绝
→ 通常不执行 Fragment Shader 循环
```

因此，从 8 层增加到 128 层仍会增加：

- CPU Draw Call 提交和排序工作；
- Vertex Shader 调用；
- 图元装配和光栅化覆盖判断；
- 深度测试工作。

但最昂贵的重复 Fragment Shader 和颜色写入可能被大量避免。完全重叠、前到后绘制的 Opaque 层数增加后，GPU Fragment 时间变化不大，正是实验希望观察到的结果。

Opaque 模式并不意味着 Fragment Shader 循环没有作用。最前面的可见层仍然会对覆盖区域执行循环，只是被遮挡层的候选片元可能在进入 Fragment Shader 之前被拒绝。

## 6. 为什么 Transparent 会重复执行循环

Demo 的透明材质使用 `ZWrite Off`。透明层可以读取已有深度并参与深度测试，但它们不会把自己的深度写回深度缓冲。

在没有其他不透明物体遮挡时：

```text
第 1 层：深度通过 → Frag 循环 → Alpha Blend → 不写深度
第 2 层：深度仍通过 → Frag 循环 → Alpha Blend → 不写深度
……
第 128 层：深度仍通过 → Frag 循环 → Alpha Blend → 不写深度
```

因此，“透明物体完全不能 Early-Z”并不严谨。更准确的说法是：

- 透明 Fragment 仍可能被场景中已有的不透明深度拒绝；
- 但当前 Demo 的透明层不会互相写入深度；
- 所以这些互相重叠的透明层通常都会通过深度测试，并执行 Fragment Shader 和混合。

## 7. Early-Z 不是绝对保证

Early-Z 是 GPU 和驱动实现的优化行为。以下因素可能让深度判断推迟，或降低提前剔除效果：

- Fragment Shader 使用 `discard` 或 `clip`；
- Fragment Shader 修改输出深度；
- Shader 具有影响执行顺序的副作用；
- 绘制顺序不是前到后；
- 特定 MSAA、Alpha-to-Coverage 或平台实现；
- Tile-Based GPU 与桌面 Immediate-Mode GPU 的架构差异。

本 Demo 的 Fragment Shader 不使用 `discard/clip`，也不输出自定义深度；Opaque 材质开启深度写入，因此属于比较适合观察 Early-Z 的受控场景。

此外，现代 GPU 可能使用 Hierarchical-Z。它可以按较大的屏幕区域提前拒绝一批候选片元，而不一定逐片元读取和比较深度。

## 8. 为什么最初在桌面电脑上看不出差距

最初的 Fragment Shader 只返回颜色，计算量很低。即使有几十层全屏透明 Quad，桌面 GPU 也可能在很短时间内完成。此时整体帧时间可能主要受以下因素限制：

- Unity Editor 开销；
- CPU 主线程或 Render Thread；
- Profiler 自身开销；
- VSync 或目标帧率；
- 当前窗口分辨率；
- GPU 本身具有较高 Fill Rate。

因此 Demo 后续增加了三个控制维度：

- 8、32、64、128 层；
- 25%、50%、100% 估算屏幕覆盖率；
- 每个 Fragment 1、8、24 次相同计算循环。

建议桌面端先使用：

```text
128 Layers
100% Coverage
24 Fragment Iterations
```

然后分别采集 Opaque 与 Transparent 的稳定帧。

## 9. 如何理解界面中的压力指标

Demo 显示两个确定性指标：

```text
Equivalent Fullscreen Layers
    = Layer Count × Coverage Ratio

Relative Fragment-Work Pressure
    = Layer Count × Coverage Ratio × Fragment Iterations
```

它们描述提交给渲染管线的潜在压力，不是硬件计数器，也不是实际执行的 Fragment 数量。

- 对 Transparent 模式，该指标更接近需要执行的相对工作量；
- 对 Opaque 模式，该指标是 Early-Z 之前的理论压力上界；
- Opaque 的实际 Fragment Shader 工作量可能远低于显示值。

## 10. Unity Profiler 中应该观察什么

### Rendering 模块

Rendering 模块主要显示：

- Batches；
- Draw Calls；
- SetPass Calls；
- Triangles；
- Vertices；
- Render Texture 等资源统计。

它可以证明两种模式的提交结构是否接近，但不能直接说明 GPU 在片元阶段花费了多少时间。

### GPU Usage 模块

GPU Usage 是独立的 Profiler 模块，用于观察 GPU 帧时间和渲染阶段耗时。可从 Profiler 左上角的 `Profiler Modules` 菜单添加。

如果 Editor 中没有 GPU Usage，或者提示当前图形 API 不支持，应使用：

1. Development Build；
2. Autoconnect Profiler；
3. 独立 Player；
4. Profiler 顶部目标切换到该 Player；
5. 关闭 VSync 或其他帧率上限。

比较时应关注稳定区间的 GPU Frame Time，而不是只看某一个瞬时 FPS 数字。

### Frame Debugger

Frame Debugger 适合验证：

- Draw 顺序；
- Render Queue；
- Blend 状态；
- ZWrite 状态；
- 每个 Pass 的实际绘制事件。

它不是精确的性能测量工具。打开 Frame Debugger 会改变运行环境，因此不能用其运行速度直接判断优化收益。

需要更深入证明 Fragment、Tile 或带宽成本时，应使用 RenderDoc、Android GPU Inspector、Xcode GPU Frame Debugger 等平台工具。

## 11. 推荐实验矩阵

每组都应保持分辨率、层数、覆盖率和循环次数一致，只切换 Opaque/Transparent：

| 实验 | Layers | Coverage | Iterations | 目的 |
|---|---:|---:|---:|---|
| 基线 | 8 | 25% | 1 | 确认固定开销与提交结构 |
| 覆盖率 | 64 | 25% / 100% | 8 | 观察屏幕覆盖面积影响 |
| 深度复杂度 | 8 / 128 | 100% | 8 | 观察重叠层数影响 |
| Fragment 压力 | 128 | 100% | 1 / 24 | 放大片元计算差异 |

预期结果不是某个固定 FPS，而是趋势：

- 两种模式的 Draw Calls 和 Renderer 数量保持相近；
- Opaque 层数增加时 GPU Fragment 成本增长较慢；
- Transparent 层数、覆盖率和循环次数增加时 GPU 时间更明显地增长。

## 12. 面试时的简短表述

可以将本实验概括为：

> 我使用相同几何、Renderer 数量、材质实例和 Fragment Shader，分别构造 ZWrite On 的不透明重叠层与 ZWrite Off 的透明重叠层。光栅化后会产生候选 Fragment；Opaque 前层写入深度后，后续被遮挡 Fragment 可由 Early-Z 在执行 Fragment Shader 前拒绝，而透明层由于不互相写深度，需要重复执行 Fragment Shader 并进行 Alpha Blend。Draw Call 数量只能描述提交结构，实际片元成本需要通过 GPU Usage 或目标平台 GPU 工具验证。

这个结论同时说明：减少 Draw Call、减少 Overdraw 和降低 Fragment Shader 复杂度是三个相关但不同的优化维度，不能只用一个 Batches 或 FPS 数字代替完整分析。

## 13. Shader 循环会不会重新从光栅化开始

不会。循环只是单次 Fragment Shader Invocation 内部的一组重复 GPU 指令，不会在每轮循环中重新执行 Vertex Shader、图元装配、光栅化或深度测试。

三层执行关系可以表示为：

```text
每个 Layer
└─ 一次 Draw Call
   ├─ Vertex Shader
   ├─ 图元装配
   └─ 光栅化
      └─ 生成多个候选 Fragment
         └─ 每个通过 Early-Z 的 Fragment 调用一次 Frag
            └─ Frag 内部执行 N 次数学循环
```

对应的概念伪代码是：

```csharp
foreach (Layer layer in layers)
{
    Rasterize(layer);

    parallel_foreach (Fragment fragment in generatedFragments)
    {
        if (!EarlyDepthTest(fragment))
        {
            continue;
        }

        Color color = Frag(fragment);
        WriteOrBlend(color);
    }
}
```

而 `Frag` 内部才包含循环：

```csharp
Color Frag(Fragment fragment)
{
    float2 value = fragment.uv;

    for (int iteration = 0; iteration < fragmentIterations; iteration++)
    {
        value = Calculate(value, iteration);
    }

    return CalculateFinalColor(value);
}
```

循环每一轮只更新当前 Fragment Invocation 使用的局部值，通常保存在 GPU 寄存器中。循环完成后只产生一次最终颜色输出，而不是每轮循环都写一次屏幕。

因此需要区分三个计数层次：

| 层次 | 重复发生的工作 |
|---|---|
| Layer | Draw Call、顶点处理、图元装配和光栅化 |
| Fragment | 深度判断和一次 Fragment Shader Invocation |
| Shader 循环 | Invocation 内部的数学或采样指令 |

## 14. 循环在 GPU 中如何执行

### 14.1 从 HLSL 到 GPU 指令

HLSL 会经过 Unity Shader 编译器、图形 API 编译器和显卡驱动，转换为 DXIL、SPIR-V 或 Metal 中间表示，最终生成目标 GPU 的机器指令。

从语义上看，动态循环可能被转换为类似下面的控制流：

```text
读取材质常量 FragmentIterations
iteration = 0
signal = 0

LOOP:
    比较 iteration 与 FragmentIterations
    如果 iteration >= FragmentIterations，跳转到 END

    执行 value 的数学计算
    执行 dot
    累加 signal

    iteration += 1
    跳转到 LOOP

END:
    计算并输出最终颜色
```

如果循环次数是编译期常量，编译器也可能进行循环展开，以更多指令体积换取更少的分支和计数开销。当前 Demo 的循环次数来自材质属性，通常需要保留动态循环或只做部分展开；最终形式由编译器和驱动决定。

### 14.2 Wave、Warp 与 Lane

GPU 不会像 CPU 那样，为每个 Fragment 启动一个完全独立的重量级线程。多个 Fragment Shader Invocation 会被组织成一个 Wave 或 Warp，例如：

```text
一个包含 32 个 Lane 的 Wave
├─ Lane 0：屏幕位置 A 的 Fragment
├─ Lane 1：屏幕位置 B 的 Fragment
├─ Lane 2：屏幕位置 C 的 Fragment
...
└─ Lane 31：屏幕位置 AF 的 Fragment
```

每个 Lane 保存自己的 UV、`value`、`signal` 和最终颜色，但同一个 Wave 中的 Lane 通常同时执行同一条 Shader 指令：

```text
全部 Lane 执行 iteration 0
全部 Lane 执行 iteration 1
全部 Lane 执行 iteration 2
...
全部 Lane 执行 iteration 23
```

可以近似理解成：

```csharp
for (int iteration = 0; iteration < 24; iteration++)
{
    parallel_for_each_lane(lane =>
    {
        lane.value = Calculate(lane.value, iteration);
        lane.signal += Dot(lane.value, lane.value);
    });
}
```

这是 SIMT/SIMD 风格的执行模型：不同 Fragment 之间大量并行，同一个 Fragment 内部有数据依赖的循环迭代则主要按顺序推进。

### 14.3 为什么循环的多轮不能同时完成

当前循环后一轮依赖前一轮产生的 `value`：

```text
value1 = F(value0)
value2 = F(value1)
value3 = F(value2)
```

因此，第 2 轮不能在 `value1` 尚未产生时完成，第 3 轮也需要等待 `value2`。编译器和 GPU 可以调度其中部分独立指令，但无法把存在这种依赖关系的 24 轮直接变成 24 个完全独立的并行任务。

GPU 的主要并行性来自同时处理大量 Fragment，而不是同时完成单个 Fragment 的所有循环迭代。

### 14.4 当前 Demo 为什么没有明显的循环分歧

`_FragmentIterations` 是材质常量。同一个 Draw Call 中所有 Fragment 读取相同的循环次数，因此一个 Wave 中的 Lane 通常会一起循环 24 次。

如果循环次数由每个 Fragment 的 UV、纹理或其他变化数据决定，就可能出现：

```text
Lane 0：循环 8 次
Lane 1：循环 24 次
Lane 2：循环 3 次
```

这会产生分支分歧。已经结束循环的 Lane 会被执行掩码关闭，但整个 Wave 通常仍需等待循环次数最多的 Lane，降低硬件利用率。

当前 Demo 使用统一循环次数，目的是避免把分支分歧混入 Overdraw 对照实验。

### 14.5 GPU 如何隐藏指令等待

当某个 Wave 等待数学指令、纹理访问或其他结果时，GPU 调度器可以切换到另一个已经准备好的 Wave：

```text
Wave A 等待
→ 执行 Wave B

Wave B 等待
→ 执行 Wave C

Wave C 等待
→ 返回 Wave A
```

这种延迟隐藏机制意味着少量循环不一定会让帧时间按循环次数线性增长。只有当覆盖 Fragment 足够多、循环足够重，并且 GPU 的可用执行资源持续被占满时，差异才会明显。

循环还会占用寄存器。寄存器使用量过高可能降低同时驻留的 Wave 数量，也就是降低 Occupancy，进一步影响 GPU 隐藏延迟的能力。

### 14.6 Early-Z 与循环 Invocation 数量

Opaque 和 Transparent 使用相同方式执行循环。两者的主要区别不是“循环如何执行”，而是“多少 Fragment Invocation 真正进入循环”：

```text
Opaque 被遮挡层
候选 Fragment
→ Early-Z 失败
→ 不启动或不激活对应的 Fragment Shader Lane
→ 不进入循环

Transparent 重叠层
候选 Fragment
→ 深度测试通过
→ 启动 Fragment Shader Invocation
→ 执行完整循环
→ Alpha Blend
```

当前循环主要进行寄存器中的数学运算，没有纹理采样，因此它构造的是相对可控的 ALU 压力。真实项目的 Fragment Shader 还可能包含纹理读取、光照、阴影采样和带宽访问，最终瓶颈需要结合具体硬件分析。

如果需要确认编译器最终采用动态循环还是循环展开，可以通过 RenderDoc 检查 Shader 中间表示，并使用 Nsight Graphics、Radeon GPU Analyzer、Xcode GPU 工具等查看更接近目标硬件的反汇编和性能计数器。
